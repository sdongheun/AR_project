# ARBusan Edge Marker Rules

이 문서는 `../planning/AR_TECH_ROADMAP.md`의 `6.4.6 projection 기반 라벨 안정화` 자식 문서다. 화면 안 후보 마커와 화면 밖 edge marker 규칙을 정리한다. 목적은 다음 작업자가 현재 구현 의도와 남은 작업을 바로 이해하는 것이다.

현재 판단:

- 2D overlay 기준의 최소 라벨/마커 안정화는 완료했다.
- 3D 라벨 배치 MVP는 VWorld Polygon 외벽 후보점, Terrain Anchor 우선 시도, WGS84 Anchor fallback, RealityKit 3D 구체/라벨 표시까지 진행했다.
- 세부 smoothing, 최종 edge marker UX, 화면 안 짧은 이름 마커 탭 승격은 3D 라벨 위치가 충분히 안정된 뒤 다시 조정한다.
- 현재 3D 마커는 실제 AR 공간의 고정 크기를 사용한다. 즉 가까우면 크게, 멀면 작게 보이도록 두고, 추후 탭 시 확대와 최대 크기 제한을 추가한다.
- 3D 라벨 고도화 작업의 상세 순서와 판단 기준은 `3D_LABEL_REFINEMENT_PLAN.md`에서 관리한다.

## 1. 용어

- 실제 라벨: 사용자가 보고 있는 주 대상의 정보 카드다. 예: `후참잘`, 거리, 신뢰도.
- matrix 마커: projection matrix 투영 위치를 확인하는 개발용 디버그 마커다. 예: `matrix 2/5`.
- 화면 안 후보 마커: 화면 안에 들어온 후보를 짧은 이름으로 표시하는 테스트용 마커다. 현재는 중심 후보 핑크, 나머지 후보 주황으로 표시한다.
- edge marker: 화면 밖 후보를 가장자리에 붙여 방향을 알려주는 검은색 마커다.
- 화면 안 후보: projection matrix 또는 허용된 FOV fallback 기준으로 현재 화면 안에 있다고 판단된 후보다.
- 화면 밖 후보: 현재 화면 안에 없어서 방향 안내가 필요한 후보다.
- 거리 반응형 표시: 사용자와 후보 사이 거리에 따라 마커 크기와 정보량을 다르게 표시하는 규칙이다.
- 3D 지리 마커: ARCore Geospatial anchor 결과를 RealityKit `AnchorEntity`에 연결해 표시하는 구체/텍스트 라벨이다.
- billboard 라벨: 3D 라벨이 사용자의 카메라를 향하도록 매 프레임 회전시키는 표시 방식이다.

## 2. 현재 구현 상태

### 2.1 실제 라벨

- 실제 라벨은 한 번에 1개만 표시한다.
- 실제 라벨 위치는 projection matrix 좌표를 우선 사용한다.
- projection matrix가 화면 밖이면 FOV fallback을 사용하되, 방향각 차이가 `75도`를 넘으면 라벨을 숨긴다.
- Scene Semantics는 점수에 반영하지 않고 라벨 위치 보정에만 사용한다.
- 현재 선택/인식된 실제 라벨 대상은 검은 edge marker에서 제외된다.

### 2.2 화면 안 후보 마커

- 화면 안 후보가 여러 개 있으면 짧은 이름 마커를 표시한다.
- 화면 중심에 가장 가까운 후보는 핑크색으로 표시한다.
- 나머지 화면 안 후보는 주황색으로 표시한다.
- 사용자가 현장 테스트에서 한 화면에 2개 이상 건물이 들어왔을 때 핑크/주황 구분이 정상 동작하는 것을 확인했다.
- 현재 핑크/주황 마커는 검증용 UI다. 최종 UX에서는 색상과 노출 조건을 다시 정리해야 한다.

### 2.3 화면 밖 edge marker

- 화면 밖 후보는 검은색 edge marker로 표시한다.
- edge marker는 짧은 이름과 방향 화살표를 표시한다.
- edge marker는 좌/우/상/하 가장자리를 모두 사용할 수 있다.
- edge marker 위치는 후보 좌표를 현재 heading/pitch 기준으로 투영한 뒤, 화면 중심에서 후보 방향으로 뻗은 선이 가장자리와 만나는 지점으로 계산한다.
- 화면 밖 edge marker는 최대 3개까지 표시한다.
- 우선순위는 카메라 중앙 방향에 가까운 순서다.
- 같은 방향에 여러 마커가 겹치면 현재는 세로로 조금씩 쌓는다.
- 실제 라벨 대상이 화면 밖으로 나가면 실제 라벨은 숨고 해당 대상이 edge marker로 안내될 수 있다.

### 2.4 거리 반응형 표시

- 기준 거리는 1km다.
- 1km 이하 후보는 기본 크기 100%로 표시한다.
- 1km 초과 후보는 78% 크기로 축소하고 짧은 거리 텍스트를 함께 표시한다. 예: `1.2km`.
- 이 규칙은 화면 안 핑크/주황 마커와 화면 밖 검은 edge marker에 모두 적용되어 있다.
- 현재 목업 건물은 대부분 1km 이내라, 거리 축소 효과는 TourAPI 재연결 또는 1km 밖 목업 추가 후 더 명확히 확인할 수 있다.

### 2.5 디버그 표시 토글

- `matrix n/m` 마커는 개발용 토글로 켜고 끌 수 있다.
- 핑크/주황 화면 안 후보 마커도 개발용 토글로 켜고 끌 수 있다.
- 실제 라벨과 검은 edge marker는 사용자용 표시이므로 현재 토글 대상이 아니다.
- 3D 라벨 전환 전까지 2D projection 결과와 3D anchor 결과를 비교하기 위해 디버그 토글은 유지한다.

### 2.6 기본 로그와 전체 로그

- 기본 화면은 현장 테스트용으로 축약한다.
- 기본 화면에는 API 키 상태, VPS/위치 요약, 데이터 상태, 현재 인식 결과, 디버그 표시 토글만 둔다.
- `전체 로그 보기` 토글을 켜면 기존 OCR, heading, pose, projection matrix, local ENU, polygon, VWorld, Scene Semantics, AR 라벨 계산 로그를 모두 표시한다.
- 전체 로그는 문제 원인 추적용이며, 기본 테스트 중에는 꺼두는 것을 기준으로 한다.

### 2.7 3D 지리 마커/라벨

- 3D 마커는 현재 RealityKit `AnchorEntity + ModelEntity`로 표시한다.
- Terrain Anchor를 먼저 시도하고, 테스트 지점에서 `errorUnsupportedLocation`이 반복되면 WGS84 Anchor fallback을 사용한다.
- WGS84 Anchor는 외부 API에서 절대고도를 받아오는 것이 아니라 앱이 계산한 절대고도 값을 ARCore에 전달한다.
- 현재 WGS84 절대고도 기준은 `ARCore Geospatial altitude + 라벨 높이 - 기기 높이 1.5m`다.
- 3D 마커 기준점은 단순 외벽 중점이 아니라 카메라 시야 방향을 기준으로 계산한 외벽 후보점이다.
- 카메라 ray가 Polygon 외벽과 교차하면 교차점을 사용하고, 직접 교차하지 않으면 ray에 가장 가까운 외벽점을 사용한다.
- 3D 라벨은 구체와 같은 anchor 아래에 붙고, 매 프레임 카메라를 향하도록 billboard 처리한다.
- 3D 구체/라벨은 거리 기반 자동 스케일 보정을 제거했다. 월드 공간 크기를 고정해 가까우면 크게, 멀면 작게 보이게 한다.
- 추후 사용자가 마커를 탭하면 선택된 구체/텍스트만 확대하고, 화면을 가리지 않도록 최대 크기 제한을 둔다.

## 3. 현장 테스트로 확인한 것

- 후참잘을 바라보면 후참잘 실제 라벨이 뜨고, 후참잘 검은 edge marker는 뜨지 않는다.
- 화면에 보이지 않는 다른 후보는 검은 edge marker로 표시된다.
- 후참잘에서 투썸 방향으로 돌리면 투썸 edge marker와 후참잘 edge marker 전환이 확인됐다.
- 한 화면에 2개 이상 후보가 들어왔을 때 중앙에 가까운 후보는 핑크, 나머지는 주황으로 표시되는 것을 확인했다.
- 디버그 UI 정리 전 현재 목업 표시 규칙은 2D 기준선으로 확인 완료했다.
- 거리 700m 정도의 더존101은 1km 목록과 edge marker에는 포함되지만, 현재 방향 후보 인식은 `CameraDirectionCandidateProvider`의 120m 제한 때문에 실제 라벨/matrix 대상으로 승격되지 않을 수 있다. 이 제한은 현재 유지하고 추후 조정한다.
- Terrain Anchor는 김해 현장 테스트에서 현재 위치 후보까지 `errorUnsupportedLocation`이 발생했다. 따라서 현재 개발 단계는 WGS84 Anchor fallback을 사용한다.
- WGS84 Anchor는 생성 완료와 `tracking` 상태까지 확인했다.
- 후참잘처럼 길 건너 건물에는 3D 구체/라벨이 표시되는 것을 확인했다.
- 투썸/올리브영처럼 너무 가까운 건물은 구체 위치를 찾기 어려운 구간이 있었고, 이는 카메라 시야 방향 기반 외벽 후보점과 크기 정책을 조정하면서 계속 확인한다.
- 3D 텍스트가 뒤집혀 보이는 문제가 있어 billboard 방향 보정을 적용했다.
- Scene Semantics와 OCR은 발열 감소를 위해 현재 비활성화했다. 비활성화 목록은 `../archive/DISABLED_FEATURES.md`에 별도로 정리했다.

## 4. 현재 유지하기로 한 제약

- 방향 후보 자동 인식 범위는 현재처럼 120m 제한을 유지한다.
- 1km 이내 후보는 목록/edge marker 대상이 될 수 있지만, 자동 라벨 후보가 되는 것은 별도 제한을 받는다.
- matrix 마커와 핑크/주황 화면 안 후보 마커는 디버그 토글로 켜고 끄며, 아직 최종 사용자 UX는 아니다.
- 긴 진단 로그는 `전체 로그 보기` 토글이 켜졌을 때만 표시한다.
- 검은 edge marker는 사용자 방향 안내용으로 유지한다.

## 5. 추가로 수정해야 할 작업

1. 디버그 UI 정리
   - 완료: `matrix n/m` 마커와 핑크/주황 후보 마커를 개발용 토글로 묶었다.
   - 완료: 기본 화면은 필수 요약만 표시하고, 기존 상세 로그는 `전체 로그 보기` 토글로 묶었다.
   - 핑크/주황 화면 안 후보 마커의 최종 색상과 노출 조건을 정한다.

2. 화면 안 다중 후보 최종 UX
   - 실제 라벨 1개 + 나머지 짧은 이름 마커 규칙은 유지한다.
   - 짧은 이름 마커 탭 시 실제 라벨로 승격하는 기능을 구현한다.
   - 여러 마커가 겹칠 때 세로 쌓기, `+N` 묶음, 우선순위를 다시 조정한다.

3. 120m 방향 후보 제한 재검토
   - 현재 더존101처럼 700m 후보는 edge marker에는 뜨지만 실제 라벨 후보로 승격되지 않을 수 있다.
   - TourAPI 관광지 연결 후 120m, 500m, 1km 중 어떤 범위가 자연스러운지 테스트한다.
   - 가까운 상점이 원거리 관광지를 가리는 문제를 함께 검증한다.

4. 거리 반응형 검증
   - 1km 밖 목업 또는 TourAPI 후보로 78% 축소와 거리 텍스트 표시를 현장 확인한다.
   - 1km 초과 후보를 탭하면 실제 라벨로 승격할지 결정한다.
   - 근거리 후보와 원거리 후보가 동시에 있을 때 우선순위를 정한다.

5. 정반대 방향 edge marker 안정화
   - 대상과 카메라 방향 차이가 180도에 가까울 때 좌/우 방향이 튀지 않도록 마지막 안정 방향을 유지하는 로직을 보강한다.
   - signed angle 디버그 로그를 추가해 현장 테스트에서 방향 계산을 확인할 수 있게 한다.

6. TourAPI 재연결 후 검증
   - 현재 목업 기반 규칙을 TourAPI 후보에도 동일하게 적용한다.
   - 건물형/비건물형 후보 분기와 edge marker 표시 규칙을 연결한다.
   - 바다/공원처럼 polygon이 없는 후보는 POI 중심 좌표 기반으로 edge marker를 표시한다.

7. 3D 마커/라벨 UX 보정
   - 상세 개선 항목은 `3D_LABEL_REFINEMENT_PLAN.md`에서 관리한다.
   - 이 문서에는 현재 표시 규칙과 완료된 체크리스트만 유지한다.

## 6. 다음 진행 순서 제안

1. 3D 라벨 고도화는 `3D_LABEL_REFINEMENT_PLAN.md`의 구현 순서를 따른다.
2. 3D 위치/높이/크기 정책이 안정되면 이 문서의 edge marker와 2D overlay 역할을 다시 정리한다.
3. TourAPI를 다시 연결해 1km 후보와 거리 반응형 표시를 검증한다.
4. 120m 방향 후보 제한을 유지할지, 1km까지 확장할지 결정한다.

## 7. 3D 라벨 배치 MVP 체크리스트

이 단계도 2D overlay 작업처럼 한 번에 전부 구현하지 않는다. 각 단계마다 실기 테스트 결과를 사용자에게 확인받고, 결과가 기대와 다르면 다음 단계로 넘어가지 않는다.

        - 선택/인식 후보의 Polygon 외곽 선분을 만든다.

        - 선택된 외벽의 양 끝점, 중점, 거리, 방향각, 길이를 로그로 표시한다.

    구현:
        - ResolvedBuildingHeight 값을 3D 라벨 후보 계산에 연결한다.
        - HEIGHT, Streetscape, 층수 추정, 기본값 중 어떤 값이 쓰였는지 로그로 표시한다.
        - 구현 완료. 사용자 실기 테스트 확인 전까지 7.3으로 넘어가지 않는다.
    사용자 테스트:
        - 건물 높이값이 말이 되는 범위인가?

[x] 7.3 Terrain Anchor 우선 + WGS84 Anchor fallback 상태 로그
    목적:
        Street View/VPS 지원 지역에서는 Terrain Anchor를 먼저 시도하고, 지원되지 않는 지점에서는 WGS84 Anchor fallback으로 3D 라벨 배치 가능성을 검증한다.
    구현:
        - Terrain Anchor를 먼저 시도하고, 테스트 결과가 지원 불가로 판단되면 WGS84 Anchor fallback으로 넘어간다.
        - 순차 테스트 후보는 외벽 중점, 외벽에서 사용자 방향 2m 지면 후보, 외벽에서 사용자 방향 5m 지면 후보, 현재 위치 지면 지원 확인 후보 순서다.
        - 외벽 중점/2m/5m 후보는 7.2 라벨 후보 높이를 지면 위 높이로 사용한다.
        - 현재 위치 지면 지원 확인 후보는 해당 지역의 Google terrain data 지원 여부를 가르는 진단용이며, 실제 건물 라벨 위치로 확정하지 않는다.
        - 모든 Terrain Anchor 후보가 `errorUnsupportedLocation`으로 실패하면 외벽 중점 좌표에 WGS84 Anchor를 생성한다.
        - WGS84 Anchor 절대고도는 우선 ARCore Geospatial altitude를 사용하고, 없으면 CoreLocation altitude를 임시 fallback으로 사용한다.
        - WGS84 절대고도 계산은 `현재 기기 고도 + 라벨 후보 높이 - 기기 높이 가정 1.5m`로 시작한다.
        - ARCore Earth tracking 상태가 tracking일 때 Terrain Anchor 생성을 요청한다.
        - anchor 생성 요청, 성공, 실패, 후보 번호, WGS84 fallback 생성 여부, tracking state를 로그로 표시한다.
        - 실제 3D 마커 표시는 7.4에서 진행한다.
        - VPS/Geospatial tracking이 약하면 anchor 생성 대기 로그만 표시한다.
        - 구현 완료. 사용자 실기 테스트 확인 전까지 7.4로 넘어가지 않는다.
    사용자 테스트:
        - Street View 지원 지역에서 Earth tracking 상태가 tracking으로 잡히는가?
        - Terrain Anchor 요청 좌표가 외벽 중점 -> 사용자 방향 2m -> 사용자 방향 5m -> 현재 위치 순서로 시도되는가?
        - 외벽 중점만 실패하고 2m/5m 후보가 성공하면 건물 외벽 좌표가 Terrain Anchor에 부적합했던 것으로 본다.
        - 현재 위치 후보까지 `errorUnsupportedLocation`이면 해당 테스트 구역은 Terrain Anchor 지원이 어렵다고 보고 WGS84 Anchor fallback으로 넘어간다.
        - Terrain Anchor 최종 실패 후 `WGS84 Anchor 생성 완료` 로그가 뜨는가?
        - WGS84 fallback의 절대고도 기준이 ARCore Geospatial altitude인지, CoreLocation altitude인지 로그로 확인한다.
    결정:
        - 김해 테스트에서 현재 위치 후보까지 `errorUnsupportedLocation`이 확인되면 현 개발 단계에서는 WGS84 Anchor fallback으로 진행한다.
        - 다만 Terrain Anchor 지원 여부는 국가/도시 전체가 아니라 실제 지점의 Google terrain/VPS 데이터 상태에 따라 달라질 수 있으므로, 부산 현장 테스트 시 같은 4단계 후보 테스트를 다시 수행한다.
        - 부산에서 Terrain Anchor가 성공하면 해당 지점은 Terrain Anchor를 1순위로 사용하고, 실패 지점은 WGS84 Anchor fallback을 유지한다.
        - WGS84 fallback은 절대고도 추정 오차가 있으므로 최종 고도 정책은 VWorld DEM, 다른 고도 API, 현장 보정값을 추후 재검토한다.
