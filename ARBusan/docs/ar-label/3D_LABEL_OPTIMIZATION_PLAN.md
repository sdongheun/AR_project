# ARBusan 3D Label Optimization Plan

이 문서는 3D 마커가 흔들리거나 건물 밖으로 벗어나는 문제를 줄이기 위한 최적화 계획이다. 현재 기준은 `3D_LABEL_REFINEMENT_PLAN.md`의 새 방향을 따른다.

## 1. 기존 방식 요약

이전 구현은 카메라 heading/ray를 기준으로 Polygon 외벽 후보점을 계산하고, 그 지점에 WGS84 Anchor와 RealityKit 구체/텍스트를 붙였다.

얻은 교훈:

- 길 건너 건물처럼 거리가 있는 경우에는 위치감이 어느 정도 맞았다.
- 가까운 건물에서는 구체가 너무 가까워지거나 외벽 앞쪽으로 튀는 문제가 있었다.
- 사용자가 좌우로 이동하면 “가장 가까운 외벽점”이 바뀌면서 마커가 따라 움직였다.
- 도심처럼 건물이 붙어 있으면 옆면/외벽 기준이 사용자에게 대상 건물을 명확히 알려주지 못할 수 있다.

따라서 외벽 부착형은 메인 UX가 아니라 fallback/디버그 참고값으로 낮춘다.

## 2. 새 최적화 원칙

- 3D 마커는 공간 위치감만 담당한다.
- 최종 상세 정보는 3D 마커 hit/tap 이벤트가 담당한다.
- 마커 좌표는 같은 POI 안에서 자주 바뀌면 안 된다.
- heading은 “사용자가 어느 방향을 보는지” 안내하는 값이지, 마커 위치를 매 프레임 옮기는 값이 아니다.
- 길찾기 모드에서는 선택 목적지 1개를 중심으로 TMAP 보행자 경로의 마지막 도착 좌표를 3D 마커 좌표로 사용한다.
- 둘러보기 모드에서는 주변 후보를 전부 3D로 띄우지 않고, 하단 반원형 2D 레이더와 카메라 보조 마커를 중심으로 한다.
- TMAP 도착점 3D 마커 높이는 우선 지면 기준 `1.7m`로 고정한다. 실외 검증 후 `1.5~1.8m` 범위에서 조정한다.
- VWorld Polygon은 필요할 때만 건물형 검증/보정/디버그에 사용한다.
- 위치가 불안정할 때는 마지막 안정 좌표를 유지하거나 2D/edge 안내로 낮춘다.

## 3. 3D 마커 좌표 우선순위

```text
1순위: TMAP 도착 좌표
    현재 위치 -> 목적지 보행자 경로의 마지막 좌표

2순위: 캐시된 TMAP 도착 좌표
    같은 POI에 대해 이전에 검증한 도착 좌표

3순위: 수동 보정 좌표
    preferredMarkerCoordinate
    entranceCoordinate

4순위: POI 좌표
    TMAP 키 없음, 호출 실패, 응답 부적합 시 fallback
```

도심/상가 밀집 구역에서는 TMAP 도착 좌표를 우선한다. 자동으로 외벽/정문을 고르는 로직만으로 목적지를 안정적으로 표현하기 어렵다.

운영 원칙:

- 부산 전체 관광지를 수동 입력하지 않는다.
- TMAP 도착 좌표를 기본으로 하고, 테스트에서 이상한 관광지만 수동 보정 리스트에 넣는다.
- 좌표 출처는 `tmapArrival`, `cachedArrival`, `manual`, `poiFallback`, `edgeOnly`로 구분한다.

## 4. 위치 안정화 규칙

### 4.1 [x] 근처 POI Anchor 선생성 실험

- 카메라가 대상을 바라보지 않아도 3D 표시 범위 안의 POI는 미리 준비한다.
- 현재 기준은 `120m 이내 생성`, `140m 밖 삭제`다.
- 여러 건물이 범위 안에 있으면 최대 5개까지 WGS84 Anchor/RealityKit Entity를 유지한다.
- 단, 이 방식은 3D 표시 검증용 자산이다. 최종 UX 기본값은 “길찾기 선택 목적지 1개 3D 마커”다.

### 4.2 [x] stable origin 사용

- raw CoreLocation을 바로 3D 계산에 사용하지 않는다.
- ARCore Geospatial 위치 정확도 10m 이내 샘플이 일정 시간 유지될 때 3D 기준 위치로 사용한다.
- 위치가 크게 튀면 바로 반영하지 않고 마지막 안정 상태를 유지한다.

### 4.3 [x] Polygon boundary 검증

- 기존 외벽 부착형 실험에서 3D 좌표가 Polygon과 무관한 지점으로 튀지 않도록 검증을 추가했다.
- TMAP 도착점 기반으로 전환하면 이 검증은 메인 필터가 아니라 디버그/보조 검증이다.

### 4.4 [x] 수동 보정 좌표 적용

- 같은 POI의 3D 마커 좌표는 한 번 확정되면 계속 유지한다.
- 사용자 위치/heading 변화만으로 마커 좌표를 다시 계산하지 않는다.
- stable origin이 크게 바뀌거나 POI 데이터가 바뀔 때만 재계산한다.
- 수동 대표 좌표가 있으면 기존 외벽 후보보다 우선한다.

현재 구현:

- `TourismSpot`에 `preferredMarkerCoordinate`, `entranceCoordinate`, `frontHeadingDegrees` 필드를 추가했다.
- `preferredMarkerCoordinate` 또는 `entranceCoordinate`가 있으면 기존 외벽 후보점보다 먼저 WGS84 Anchor 후보로 사용한다.
- 수동 마커 좌표는 건물에서 조금 띄울 수 있도록 Polygon 내부 또는 외곽 8m 이내를 허용한다.

### 4.5 [x] TMAP 도착 좌표 적용

테스트:

- TMAP 마지막 도착 좌표가 POI 중심이 아니라 접근 가능한 도로/입구 쪽으로 보정되는가?
- 후참잘/투썸/올리브영/더존101에 대해 도착 좌표가 안정적으로 캐시되는가?
- 앱을 켠 뒤 같은 목적지를 좌우로 보거나 걸어도 마커가 계속 재생성되지 않는가?

현재 상태:

- TMAP API 키 연결, 클라이언트, 마지막 좌표 파싱, 캐시는 구현했다.
- 실외에서 실제 구체/마커 위치 정합성은 아직 검증하지 못했다.
- 앞으로는 둘러보기의 주변 후보 3D 동시 표시보다 길찾기 목적지 1개 3D 표시를 우선 안정화한다.

### 4.6 [ ] 둘러보기 반원형 2D 레이더 MVP

- 하단 반원형 UI에 내 위치, 현재 heading, 주변 후보 방향/거리 마커를 표시한다.
- 카메라에는 화면 안 후보 또는 선택 후보만 가볍게 표시한다.
- 후보 탭 시 길찾기 목적지로 승격할 수 있게 한다.

### 4.7 [ ] 경로 화살표 MVP

- TMAP 보행자 경로 좌표열을 AR 공간으로 변환한다.
- 지면 또는 화면 보조 UI에 이동 방향 화살표를 표시한다.
- 3D 구체는 도착 지점, 화살표는 이동 방향을 담당한다.

### 4.8 [ ] 방향 문구 smoothing

- heading이 조금 흔들려도 방향 문구가 빠르게 바뀌면 안 된다.
- 예: `오른쪽 앞 -> 오른쪽 -> 오른쪽 앞`이 짧은 시간에 반복되면 마지막 안정 방향을 유지한다.

### 4.9 [ ] 비건물형 POI fallback

- 비건물형도 TMAP 마지막 도착 좌표를 사용한다.
- TMAP 결과가 없으면 TourAPI POI 좌표점 기준으로 3D/2D/edge 표시를 만든다.

## 5. 로그 정리 기준

기본 로그:

- 현재 3D 기준 위치 상태
- 활성 Anchor 개수
- POI별 마커 좌표 출처
  - TMAP 도착 좌표
  - 캐시된 도착 좌표
  - 수동 보정 좌표
  - POI fallback
- 2D/3D 표시 상태

전체 로그:

- VWorld Polygon 후보
- TMAP 보행자 경로 응답/마지막 좌표
- WGS84 Anchor 요청/완료/실패
- ENU 좌표
- projection matrix 비교
- 기존 외벽 후보점 디버그

## 6. 완료 기준

- 둘러보기 모드에서 하단 반원형 레이더가 주변 후보 방향/거리를 이해시키는가.
- 길찾기 모드에서 선택 목적지 마커는 TMAP 도착 좌표에 고정된다.
- 사용자가 좌우로 움직여도 같은 POI 마커가 계속 따라오지 않는다.
- 가까운 목적지는 3D 마커로 위치감을 주고, 경로 화살표로 방향을 안내한다.
- 120m 밖 후보는 3D를 숨기고 2D/edge marker로 방향과 거리를 안내한다.
- TourAPI 건물형/비건물형 후보에 같은 TMAP 도착점 규칙을 적용할 수 있다.
